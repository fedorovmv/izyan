# Архитектура

Документ для пользователя: из чего состоит анализатор, как данные
текут по конвейеру, какими средствами работает каждая часть и где
проходит граница между детерминистическим кодом и LLM.
Внутренняя механика — [`dev/current/analysis-internals.md`](dev/current/analysis-internals.md).

## 1. Контекст системы

```text
   advisory (CVE/GHSA/GO-*)        репозиторий продукта (snapshot)
            │                              │
            ▼                              ▼
   ┌─────────────────────────────────────────────────┐
   │                 vuln-analyzer                   │
   │  affected? → условия эксплуатации → evidence    │
   │  → claims → negative check → review → verdict   │
   └─────────────────────────────────────────────────┘
            │
            ▼
   verdict + report.{json,md} + openvex.json + cyclonedx.json
```

Входы:

- **advisory** — OSV API или `--vuln-file`;
- **снимок продукта** — путь к Go-репозиторию, опционально `--binary`
  (build info), `--release-go-version`, `--ticket` (generic intake);
- **флаги режима** — `--deterministic-only`, `--allow-exec`,
  `--case-dir`, бюджеты.

## 2. Поток обработки

Анализ идёт по функциональным блокам. Каждый блок отвечает на один
вопрос; ответ блока — вход следующего.

```text
 advisory + снимок продукта
            │
            ▼
 ┌─────────────────────────┐
 │ 1. Применимость         │  go list -m all, semver-диапазоны,
 │                         │  go.mod, build info бинаря
 └─────────────────────────┘
            │ нет → вердикт NOT_AFFECTED, конец
            ▼
 ┌─────────────────────────┐
 │ 2. Первопричина         │  git-diff фикс-коммита + AST-поиск
 │                         │  символов в зависимости; LLM-кандидаты
 └─────────────────────────┘
            ▼
 ┌─────────────────────────┐
 │ 3. Модель эксплуатации  │  pattern library (CWE→шаблоны
 │                         │  условий); LLM дополняет
 └─────────────────────────┘
            ▼
 ┌─────────────────────────┐
 │ 4. Сбор доказательств   │  govulncheck + собственный анализ
 │                         │  кода (AST/типы): provenance, гарды,
 │                         │  listeners, конфиги
 └─────────────────────────┘
            ▼
 ┌─────────────────────────┐
 │ 5. Оценка условий       │  детерминистические evaluators
 │                         │  поверх собранных фактов
 └─────────────────────────┘
            ▼
 ┌─────────────────────────┐
 │ 6. Проверка опровержений│  verifier: поиск обходных путей —
 │                         │  callers, reflect/unsafe, build-tag,
 │                         │  interface dispatch
 └─────────────────────────┘
            ▼
 ┌─────────────────────────┐
 │ 7. Ревью → Вердикт      │  structural checks + LLM-ревьюер;
 │      → Отчёт            │  вердикт — только код
 └─────────────────────────┘
```

### Чем каждый блок отвечает и как работает

| Блок | Отвечает на вопрос | Чем отвечает |
|---|---|---|
| Применимость | «уязвимый код вообще есть в продукте?» | `go list -m all` + `vendor/modules.txt` (модуль/версия), `go list -deps` (пакет), semver-диапазоны из advisory, `go version -m` бинаря (toolchain для std-advisory) |
| Первопричина | «где в зависимости сломанное место?» | `git diff` фиксирующего коммита → список изменённых символов → каждый проверен AST-поиском в исходниках зависимости; LLM предлагает кандидатов при скудных advisory-данных |
| Модель эксплуатации | «что должно совпасть, чтобы сработало?» | класс уязвимости (CWE-маппинг/keywords) → декларативные паттерны условий; LLM дополняет — все предложения проверяются поиском в коде зависимости |
| Сбор доказательств | «что реально делает продукт?» | **govulncheck** — пути от точек входа до уязвимых символов; **собственный анализ** (AST/SSA/типы) — provenance аргументов, гарды до sink'а, listeners/dial, конфиги, write-маркеры |
| Оценка условий | «выполняется ли условие?» | детерминистические evaluators по видам условий (достижимость, контроль атакующего, ограничение входа, валидация, конфиг, билд) |
| Проверка опровержений | «точно ли условие невыполнимо?» | verifier: оставшиеся ссылки на символ, dynamic-маркеры (func_value/linkname/reflect-write/unsafe), build-tag-исключённые файлы, interface dispatch |
| Ревью → Вердикт → Отчёт | «можно ли доверять выводу?» | structural checks (TRUE без evidence, FALSE без NV, висячие ссылки) + LLM-ревьюер (семантические ошибки); вердикт по таблице гарантий — только код |

### Ограниченные циклы внутри потока

- **Уточнение «неизвестно»** — условие, которое не удалось оценить,
  порождает гипотезу («данные резолвятся глубже в caller-цепочке»);
  целевое действие (углублённый трейс, dynamic-скан) собирает ещё
  факты, условие переоценивается — до фикспоинта или потолка попыток.
  Детерминистические экшены исчерпаны → один bounded LLM-шаг.
- **Перепроверка опровержения** — обязательна до вердикта, опирающегося
  на «условие невыполнимо».
- **Ревью ↔ исправление** — находки ревью могут только понижать
  утверждения до «неизвестно»; после исправления ревью повторяется
  (не более 2 раундов).

Порядок принципиален: **сначала дешёвые факты о зависимостях, затем
дорогой анализ кода, LLM — в конце каждого блока как fallback**.
Если применимость не подтверждена — анализ кода и LLM не запускаются.

Весь промежуточный состояние кейса пишется на диск после каждого блока
— прогон можно перезапустить, он не зависит от LLM-истории диалога.

## 3. Разделение ролей: код и LLM

LLM — слой поверх детерминистического ядра. Он **предлагает
структуры**; код **верифицирует и решает**.

| Стадия | Детерминистический код | LLM (опционально) |
|---|---|---|
| SNAPSHOT_PRODUCT | вся стадия | — |
| RESOLVE_VULNERABILITY | вся стадия | — |
| CHECK_AFFECTED | вся стадия: `go list`, semver, build | — |
| RESOLVE_ROOT_CAUSE | fix-commit diff, `FindSymbol`-верификация каждого кандидата в dep source | предлагает кандидатов при недостатке advisory-данных (retry-loop) |
| BUILD_EXPLOIT_MODEL | `Classify` по CWE/keywords → декларативные паттерны → generic fallback; LLM-предложения верифицируются `FindSymbol` | дополняет условия, предлагает subjects (datum/pair) |
| COLLECT_EVIDENCE | вся стадия: govulncheck + `goanalysis` | — |
| EVALUATE_CONDITIONS | вся стадия: evaluator-цепочка | — |
| GAP_ANALYSIS | планировщик гипотез + детерминистические tool-экшены; LLM-fallback **только после исчерпания** детерминистики | предлагает фальсифицируемую гипотезу + один tool call (bounded) |
| NEGATIVE_CHECK | вся стадия: `Verifier` | — |
| REVIEW | structural checks: TRUE без evidence, FALSE без NV, dangling refs | семантический ревьюер: patch misinterpretation, scope mismatch |
| REPAIR_ANALYSIS | вся стадия: только демоция claims до UNKNOWN | — |
| EVALUATE_VERDICT | вся стадия: матрица вердиктов | — |

Правила границы:

- LLM не может **усилить** вывод: LLM-TRUE не заменяет доказуемый
  FALSE, LLM-FALSE не создаёт вердикт без falsifier + NV.
- LLM может **ослабить**: ревьюер демотирует claim в UNKNOWN по
  конкретной находке — это safe-направление, поэтому допустимо.
- Отказ/ошибка LLM → детерминистический fallback + limitation;
  `--deterministic-only` гасит слой целиком.
- Все вызовы LLM — через bounded typed tools с бюджетом и
  evidence-регистрацией; tool miss возвращается модели как ошибка.

## 4. Средства анализа

- **govulncheck** — authoritative оракул reachability по call graph;
  его молчание различается на «advisory не в БД» vs «пути нет» и само
  по себе вердиктом не становится.
- **Статический анализ** (`internal/goanalysis`) — то, чего govulncheck
  не делает: provenance аргументов, валидации до sink'а,
  deployment-факты (listeners, dial, конфиги), альтернативные пути.
- **Exploit pattern library** (`internal/exploit`) — условия по классу
  уязвимости вместо одной generic-модели.
- **Target toolchain** (`internal/toolchain`) — анализ `std`-advisory
  под версией Go реального релиза, не локальной.
- **Knowledge base** (`internal/goanalysis/knowledge.json`, embedded)
  — семантика экосистемы как данные, не код: какие вызовы производят
  какой origin, passthrough/populate-семейства, config-теги, listener-
  примитивы. Подробнее — §4.1.

### 4.1. База знаний экосистемы — зачем она отдельным компонентом

Provenance и exposure-анализ сводят вопросы «откуда пришли данные»,
«открыт ли listener», «какой источник у конфига» к семантике
экосистемных API: `os.Getenv` — источник `CONFIGURATION`,
`io.ReadAll` пробрасывает данные из аргумента, `net.Listen` открывает
порт, тег `env` маркирует конфиг-поле. Набор таких записей и есть база
знаний. От неё напрямую зависит вердикт: пропущенная запись → origin
не резолвится → `UNKNOWN`; неверная запись → неверный origin →
неверный вывод. Поэтому база — данные с жизненным циклом, а не
литералы в коде:

- **Расширяемость**: у продукта есть свои библиотеки (corp-config,
  framework-хелперы), о которых встроенная база не знает.
  `--knowledge <json>` добавляет записи без пересборки; мерж только
  аддитивный, переопределение значения — ошибка (тихая перезапись
  семантики опаснее пропуска).
- **Аудируемость**: одна таблица в JSON ревьюится целиком — видно все
  доверенные источники, а не размазанные по файлам мапы.
- **Версионируемость**: `schema_version` маркирует формат (совмести-
  мость при смене схемы), `data_version` — ревизию содержимого.
- **Воспроизводимость**: отчёт пишет `sources=[name@data_version]`
  и `digest=sha256` смёрженной базы — вердикт привязан к конкретной
  ревизии семантики, а не «какой-то сборке анализатора».

Граница содержимого: только универсальная семантика публичных API
экосистемы. Продукт-специфика и локальные константы в базу не
попадают — они подаются оверлеем конкретного прогона (правило
`agent-rules/generality.md`).

## 5. Модель данных

- `AnalysisCase` — персистентный кейс: advisory, snapshot, affected,
  root cause, exploit model, evidence graph, claims, reviews, verdict.
- `EvidenceGraph` — evidence с provenance и хэшами: call paths,
  data flows, entrypoints, validations, exposure/config факты,
  вызовы инструментов, ограничения покрытия.
- `Claim` — текущее состояние условия (TRUE/FALSE/UNKNOWN) + evidence +
  falsifier + результат negative verification + limitations.
- `Hypothesis` — аудируемый след gap-analysis: что пробовали.

## 6. Границы процесса

Сборка, тесты и прочий exec в анализируемом репозитории — только за
`--allow-exec`; все вызовы внешних инструментов аудируются
(`tool_executions`: args, exit code, sha256 вывода, длительность).
