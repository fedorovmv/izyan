# Спецификация: Точность рефлексивных демоций и субъектно-ориентированная непрозрачность (B19)

**Дата:** 2026-10-04  
**Статус:** Согласовано  
**Бэклог:** B19 («Точность reflect/unsafe демоций NV», дефект D4 из `eval/ground-truth.md`)  
**Целевой кейс:** `ghsa-465g-fh3v-9jw4` в `eval/live-corpus.json` на промышленном репозитории (`${VA_PRODUCT_REPO}`)

---

## 1. Контекст и мотивация

При анализе реального сервиса на уязвимости библиотеки `github.com/rabbitmq/amqp091-go v1.10.0` кейс `GHSA-465g` (инъекция параметров в `amqp091.URI.String`) завершается вердиктом `INCONCLUSIVE`, хотя истинный вердикт — `NO_EXPLOIT_PATH_FOUND`:
1. **Продукт не использует уязвимый функционал:** метод `URI.String()` никогда не вызывается в коде продукта (0 вызовов, тип `amqp091.URI` продуктом не создаётся и не принимается).
2. **Ложная непрозрачность в `ModuleInternalReach`:** в кодовой базе зависимости присутствуют косвенные вызовы через переменные функций (например, сетевой диалер `dialer("tcp", addr)` в `DialConfig`). Текущая реализация помечает весь граф вызовов модуля как непрозрачный (`opaque = true`), блокируя доказательство отсутствия вызова для `URI.String()`, несмотря на то, что сигнатура сетевого диалера несовместима с целевым методом.
3. **Ложная демоция рефлексии (дефект D4):** при наличии в коде продукта вызовов `reflect.Value.MethodByName` негативная верификация предполагает потенциальное расширение графа вызовов для любого экспортированного метода. Однако в Go динамический вызов метода через рефлексию невозможен без экземпляра соответствующего типа в памяти. Если тип `amqp091.URI` продуктом не инстанцируется, рефлексия не может его вызвать.

Цель данной фичи — реализовать субъектно-ориентированную проверку непрозрачности вызовов и учет инстанцирования типов ресиверов при анализе рефлексии, позволив безопасно и строго доказать вердикт `NO_EXPLOIT_PATH_FOUND` для `GHSA-465g` без ущерба для безопасности (`false-safe = 0`).

## 2. Архитектура и алгоритмы

### 2.1. Субъектно-ориентированная непрозрачность (`ModuleInternalReach`)
В `internal/goanalysis/source.go`:
- Вместо бинарной пометки вызывающей функции в `opaqueCallers` регистрируется подробный контекст каждого непрозрачного сайта вызова:
  - Сигнатура вызываемой переменной функции (`*types.Signature`);
  - Интерфейсный тип (для интерфейсных вызовов без прямых реализаций).
- При обходе BFS от продуктовых точек входа к непрозрачным сайтам:
  - Непрозрачный вызов считается блокирующим для конкретного субъекта только в том случае, если он *потенциально совместим* с этим субъектом:
    - **Для функциональных переменных:** сигнатура непрозрачного вызова идентична или структурно совместима с сигнатурой субъекта (совпадает число параметров, их типы и возвращаемые значения). Вызов `dialer("tcp", addr)` с сигнатурой `func(string, string) (net.Conn, error)` не может передать управление в метод `URI.String` с сигнатурой `func() string`.
    - **Для интерфейсных вызовов:** тип ресивера субъекта должен реализовывать вызываемый интерфейс, а сам интерфейс должен содержать метод с именем субъекта.
- Если ни один достижимый непрозрачный вызов не совместим с субъектом, отсутствие вызова субъекта считается доказанным (`opaque = false`).

### 2.2. Учет инстанцирования типов в Negative Verification (`negative.go`)
В `internal/goanalysis/negative.go`:
- При анализе маркера `reflect_method` (`reflect.Value.MethodByName` / `Method`) для субъектов-методов:
  - Выполняется проверка, инстанцирован ли тип ресивера субъекта (`amqp091.URI`) в коде продукта.
  - Проверка использует индекс конкретно создаваемых типов (`ix.instantiated()` / `instantiatedNamed`): литералы структур, `new()`, `make()`, явные переменные типов, а также типы, возвращаемые или принимаемые используемыми продуктом API функций зависимости.
  - Если тип ресивера нигде не создаётся и не передаётся в продукт, вызов `MethodByName` в стороннем коде продукта физически не имеет объекта этого типа для вызова.
  - В этом случае маркер `reflect_method` игнорируется для данного субъекта и не добавляет ограничение *"widens the call graph"*, предотвращая ложную демоцию вердикта структурным ревьюером.

## 3. Инварианты и безопасность

1. **Генеральность (`docs/agent-rules/generality.md`)**:
   - Никаких строковых литералов или путей вида `amqp091`, `URI`, `String` в коде анализатора (`internal/goanalysis/`, `internal/evaluator/`).
   - Логика строится исключительно на правилах системы типов Go (`go/types`): `types.Identical`, `types.Implements`, проверка набора полей и параметров сигнатур.
2. **Безопасность отрицательных вердиктов (`false-safe = 0`)**:
   - Если сигнатура непрозрачного вызова совпадает с сигнатурой субъекта или тип ресивера реально инстанцирован в продукте, анализатор строго сохраняет консервативное поведение (`UNKNOWN`).
3. **Локальность коммитов**:
   - Все изменения коммитятся строго локально в Git; `git push` выполняется единожды в финале задачи.
