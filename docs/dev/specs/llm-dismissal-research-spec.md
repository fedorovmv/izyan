# LLM-assisted отклонение находок: исследовательская спецификация

Статус: согласованные цели и направления; исследовательские гипотезы не
подтверждены. Исследование и реализация анализатора не запускались при
сохранении документа.

План исполнения:
[`llm-dismissal-research-plan.md`](../plans/llm-dismissal-research-plan.md).

## 1. Зачем это продукту

Цель — давать дополнительную ценность относительно standalone govulncheck
на известных уязвимостях, которые тот сообщает как `reachable` или
`package-level`. Основной интерес — доказательное отклонение находок,
а не пересказ advisory или повторный поиск call path.

Выбран гибрид:

- машинно проверенное достаточное доказательство может поддерживать
  автоматическое отклонение в рамках инвариантов анализатора;
- аргументы с незакрытыми обязательствами становятся досье для эксперта,
  не меняя автоматически safe-verdict;
- контекстная критичность и приоритет исправления являются отдельными
  результатами, а не заменой exploitability verdict.

Рабочая гипотеза — LLM полезна для выбора, формулирования и сборки
локального достаточного доказательства. Она не заменяет проверку
необходимости условия дефекта и полноты охвата.

Первый срез — исследование и досье. Production-checker, новые evaluators,
condition kinds, falsifiers и изменения negative verification в этот
срез не входят.

## 2. Уже существующее и новая ставка

LLM-слой уже предлагает root-cause candidates, exploit conditions,
гипотезы для сбора evidence и reviewer findings. Само увеличение числа
tool calls не создаёт новое доказательство, если доступные инструменты
не способны проверить требуемое свойство.

Новая ставка — проверяемые артефакты: точное необходимое условие,
локальный proof obligation, проверенная семантическая summary или
структурированное экспертное досье. Вклад LLM надо измерять отдельно
от пользы нового детерминистического механизма и ручного исследования.

В описанном в `eval/README.md` baseline дополнительное снятие составляет
1/22 сигналов и 0/17 `reachable` (исправленная разметка: module-level
находки не считаются package-level сигналом; единственный package-level
cleared — `real-unix-stat` — уже имел no-call результат govulncheck).
Это результат конкретного прогона, не прогноз для других продуктов и не
baseline нового исследования. Новое сравнение требует свежих результатов
на одинаковых входах, toolchain и сопоставимой БД.

## 3. Направления, которые сохраняем

### 3.1. Выбор самого локального доказательного маршрута

LLM предлагает несколько альтернативных оснований отклонения и выбирает
то, которое требует минимального достаточного охвата. Например:
невозможный режим, запрещённый диапазон, обязательная validation,
несовместимый тип или недостижимое состояние объекта.

Реальный якорь класса «невозможный режим» (feature gate): `GO-2026-6443` —
дефект проявляется только в сервере, сконфигурированном через
`xds.NewGRPCServer`; generic transport-путь reachable, но режим отсутствует
в сборке. Подобные условия — наличие конструктора/пакета в графе —
проверяемы локально, без ingress closure.

- Артефакт: falsifier-кандидат и список обязательств с точками проверки.
- Граница доверия: выбор маршрута не является доказательством.
- Блокеры: обходные вызовы, alias, callbacks, runtime overrides,
  незакрытый набор relevant paths.
- Проверка пользы: достаточное основание найдено на сигнале govulncheck
  и сохраняется на контрольных вариантах без case-specific хардкода.

### 3.2. Точное условие дефекта из advisory и fix series

LLM сопоставляет advisory, уязвимый код, все relevant fix artifacts и
regression tests, затем предлагает необходимое условие проявления именно
этой уязвимости.

Два обязательства проверяются раздельно:

1. Условие действительно необходимо для рассматриваемого дефекта.
2. Условие не выполняется на всех relevant путях snapshot продукта.

- Артефакт: условие с привязкой к версии, механизму дефекта и исходникам.
- Граница доверия: правильный symbol и валидный JSON не доказывают
  семантическую необходимость условия; fix diff сам по себе не доказывает
  единственность exploit mechanism или полноту sink set.
- Блокеры: неполная fix series, ambiguous root cause, альтернативные
  механизмы или sinks вне сформулированного predicate.
- Проверка пользы: условие позволяет построить меньшее проверяемое
  доказательство, не ослабляя negative verification.

### 3.3. Проверяемые семантические summaries библиотек

LLM предлагает, какие аргументы и состояния влияют на значение, какие
поля читаются или записываются, какие источники используются и какие
ограничения сохраняются после преобразования.

- Артефакт: summary с обязательствами проверки и hash/version binding.
- Граница доверия: использовать summary для отрицательного вывода можно
  только после подтверждения её релевантных утверждений.
- Блокеры: скрытые источники, aliasing, mutable state, concurrency,
  непрозрачный dispatch; доказать отсутствие других чтений сложнее,
  чем найти одно чтение.
- Проверка пользы: summary закрывает локальный UNKNOWN и переносится
  на независимые продукты. Если проверка требует универсального
  Go-анализатора, ожидаемый выигрыш не подтверждён.

Первый срез не реализует summaries; это резерв при конкретном blocker.

### 3.4. Экспертное досье

Досье содержит предлагаемое основание отклонения, установленные факты,
предположения, исходники и конфигурацию, альтернативные пути,
недостающие проверки, scope и условия пересмотра решения.

- Артефакт: воспроизводимый пакет аргументов, а не свободное заключение
  «скорее всего безопасно».
- Граница доверия: экспертное решение хранится отдельно; оно не
  превращает `UNKNOWN` в машинное `VERIFIED`.
- Блокеры: неподтверждённые факты окружения, отсутствие актуального
  snapshot или основания достаточности.
- Проверка пользы: эксперт принимает аргументацию при меньших затратах
  времени; это отдельная метрика, не автоматический cleared rate.

### 3.5. Поиск контрпримеров

LLM пытается разрушить основание отклонения: другой constructor или
call site, callback, преобразование, запись после проверки, автономный
источник dependency, runtime mode или альтернативный deployment.

- Артефакт: конкретный путь или воспроизводимая проверка, опровергающая
  предпосылку.
- Граница доверия: найденный контрпример разрушает основание; отсутствие
  контрпримеров и согласие нескольких моделей не доказывают безопасность.
- Блокеры: недостаточный охват поисковых инструментов и неверная модель
  атакующего.
- Проверка пользы: заведомо ложные основания не принимаются, включая
  constant URL, после которого dependency читает внешнее содержимое.

### 3.6. Документация и рекомендации использования

LLM извлекает поддерживаемые режимы, опасные опции, trust boundaries,
ограничения входа, deployment requirements и рекомендации mitigations,
затем связывает их с условиями конкретной CVE.

- Артефакт: условие безопасного использования с источником и версией
  документации, проверкой достаточности и проверкой применения.
- Граница доверия: рекомендация отключить feature не доказывает её
  отключение в продукте. «Безопасно при A и B» не означает «A и B выполнены».
- Блокеры: документация другой версии, неясные defaults, пользовательские
  extensions, неизвестная фактическая конфигурация.
- Проверка пользы: общий совет превращается в конкретное проверяемое
  обязательство или экспертное основание с явными предпосылками.

### 3.7. Deployment, манифесты и конфигурация

Проверяемая цепочка:

```text
параметр deployment
  -> итоговое значение после overrides
  -> чтение значения приложением
  -> конкретное поведение или ветка
  -> отсутствие обязательного условия CVE
```

Различать рекомендации, templates, rendered manifests, effective config
и подтверждённое фактическое состояние. Наличие policy-файла не является
само по себе доказательством применения или полноты сетевого ограничения.

- Артефакт: deployment-bound proof obligation, evidence применения,
  охват всех relevant routes и способы инвалидирования вывода.
- Граница доверия: внутренний сервис или authenticated input не
  объявляются автоматически безопасными; ограничение поверхности не
  обязательно исключает эксплуатацию.
- Блокеры: незакрытые overrides, gateways, прямые listeners, outbound
  responses, callbacks, неприменённые policies, runtime changes.
- Проверка пользы: конкретный deployment даёт доказательное основание
  отклонения либо более точное досье, невозможное из reachability alone.

Изменение deployment не должно молча распространяться на весь продукт.

### 3.8. Контекстная критичность и приоритет

Сохранять отдельно:

- исходную severity и её источник;
- контекстную оценку для продукта и deployment;
- рекомендуемый priority/SLA;
- exploitability verdict и силу доказательства.

Контекст может понижать или повышать оценку. Если используется численный
CVSS Environmental score, его calculation и mapping metrics должны
проверяться отдельно; LLM не присваивает число произвольно.

- Артефакт: reasoned contextual assessment с версией, deployment,
  моделью атакующего, facts/assumptions и условиями пересмотра.
- Граница доверия: меньший приоритет не является proof of non-exploitation
  и не даёт `NOT_AFFECTED`.
- Блокеры: неполная модель последствий и активов, неподтверждённое
  применение защитных мер, неизвестная экспозиция.
- Проверка пользы: оценка и очередь исправления точнее для конкретного
  окружения; не смешивать эту пользу с signal-cleared rate.

## 4. Первый срез: локальный type gate в jose2go

Выбран `GO-2023-2409` / `CVE-2023-50658` и `jose2go v1.5.0`.

При предварительном чтении обнаружено расхождение: существующий
`real-jose-decrypt` передаёт `[]byte`, а просмотренная PBES2-ветка
derivation требует успешного `key.(string)`. Это кандидат на локальное
основание отклонения, не установленный safe-verdict и не уже завершённая
коррекция ground truth.

Исследование должно:

1. Проверить necessity условия по advisory, исходникам и fix artifacts.
2. Проследить actual key resolution, включая callbacks и преобразования.
3. Перечислить relevant derivation sites и явно ограничить coverage.
4. Сравнить bytes-, string-, callback- и deployment-dependent варианты.
5. Получить свежий baseline govulncheck и результаты существующего
   deterministic/LLM pipeline на этих же snapshots.
6. Собрать досье и выбрать следующий шаг по фактам, а не по желаемому verdict.

Следующий альтернативный proof route — ограничение входа до JWS, при
котором JWE/PBES2 не допускается. Этот route не входит в первый срез и
не должен подменять опровергнутую гипотезу типа ключа без нового дизайна.

## 5. Доказательства, метрики и ограничения

Главные инварианты проекта сохраняются. Особенно:

- LLM создаёт structured proposals, не авторитетные facts или verdicts.
- `FALSE` требует falsifier и successful negative verification;
  `NO_EXPLOIT_PATH_FOUND` — `VERIFIED` на mandatory condition.
- `NOT_AFFECTED` остаётся результатом детерминистической affected-цепочки.
- `UNKNOWN` — допустимый терминальный результат.
- Source audit и обычные тесты не становятся автоматически persisted
  `VERIFIED` evidence анализатора.
- `KNOWN_ONLY` не заменяется `COMPLETE` по одному списку symbols или diff.
- Отсутствие воспроизведённого DoS не доказывает невозможность DoS.
- Контроли с callback и deployment-dependent типом нельзя снимать на
  основании статического типа исходного аргумента.
- Никакого CVE/product-specific хардкода в проверяющем механизме.

Отдельно измерять:

1. **Автоматическое снятие:** safe-verdict с требуемым доказательством
   на `reachable`/`package-level` baseline.
2. **Экспертную пользу:** качество и стоимость проверки досье;
   acceptance не переименовывается в машинное снятие.
3. **Вклад LLM:** обнаружение relevant condition, mapping и контрпримеров
   против того же deterministic pipeline, с раскрытием ручных подсказок.
4. **Безопасность:** ни положительные, ни unresolved контроли не получают
   необоснованного safe-verdict.

Исследовательский корпус без `expect` не имеет достаточного oracle для
его метрики `false-safe`. Его выводы не добавляются к production cleared
rate автоматически.

## 6. Выход исследования и проектный шлюз

Статус — `CONDITIONAL` для исследования; реализация checker не утверждена.

Открытые вопросы:

- necessity выбранного условия и полнота relevant paths;
- ground truth прежнего `real-jose-decrypt`;
- способность текущих LLM adapters самостоятельно найти нужный маршрут;
- стоимость будущей генеральной машинной проверки.

Итог досье — один из результатов:

- **Перспективно для checker:** локальное основание достаточно и
  проверяемо; next slice получает отдельный контракт.
- **Полезно для эксперта:** аргументы полезны, но существенное
  proof obligation остаётся открытым.
- **Гипотеза опровергнута:** назван конкретный путь или неверная предпосылка.

При обнаружении факта, меняющего доказательство, trust boundary или
coverage, не адаптировать production-архитектуру скрытно: записать
опровергнутое допущение и вернуться к проектированию.

## 7. Внешний реестр реальных кейсов отклонения

Пул реальных кейсов отклонения (сопоставление публичных advisory с
реальными продуктовыми снапшотами, человеческими основаниями триажа и
результатами прогонов анализатора) ведётся в приватном реестре **вне
этого репозитория**. Реестр содержит внутренние имена компонентов,
локальные пути и данные тикетов — поэтому не коммитится.

- Локальный резолв: каталог реестра задаётся через `VA_RESEARCH_ROOT`
  (env), файл `case-pool-20260930.md`. Приватные пути в tracked
  документах не фиксируются.
- В репозитории допустимы только публичные якоря — advisory ID
  (`GO-2026-6443`, `GO-2026-4762`, `GO-2026-4526`, `GO-2026-6303`,
  `GO-2026-4950`, `GO-2026-5841`, `GO-2026-5942`, `GO-2026-5024`,
  `GO-2026-5025..5030`, `GO-2026-5932`, `GO-2026-6372`, `GO-2026-5970`,
  `GHSA-rm6m-hrcw-jw33`, `GHSA-33mj-cw25-m34h` и др.) и обобщённые классы
  оснований (`GATE-FEATURE`, `SYM-ABSENT`, `PKG-ABSENT`, `CFG-BOUND`,
  `CFG-EXPR`, `PLAT`, `TRUST`, `FIXED`).
- Человеческие отклонения в тикетах — гипотезы для проверки, не ground
  truth. В реестре зафиксированы совпадения и расхождения с независимым
  аудитом (например, по `GO-2026-5970` аргументация «нет вызовов» неточна
  при reachable-сигнале — основание должно опираться на provenance входа).
- Для каждого необходимого условия реестр фиксирует домен контроля:
  `ATTACKER` (данные с провода), `ADMIN` (конфиг/deployment — пользователь
  API его не контролирует), `DEPLOY` (окружение сборки), `LIBRARY`
  (внутренний протокольный контракт). `ADMIN`-условие отклонимо только при
  аудите всех источников конфигурации — «значение задано конфигом» само по
  себе не является отрицательным доказательством; иначе случай — досье
  эксперту (`TRUST`).

### 7.1. Классификация пула по основаниям и доступным доказательствам

Пул после дедупликации — 14 кейсов (тикеты с одинаковым advisory и
основанием слиты). Классы оснований и то, какое доказательство каждый
допускает:

| Основание | Кейсы | Доступное доказательство | Маршрут |
|---|---|---|---|
| **Отсутствие кода** — пакет/символ дефекта вне build graph (`PKG-ABSENT`, `SYM-ABSENT`, `GATE-FEATURE`) | GO-2026-6443, GO-2026-4762, GO-2026-6303, GO-2026-4950, GO-2026-5841, GO-2026-5025..5030, GO-2026-5942, GO-2026-6441, GO-2026-5932 (9/14) | persisted `go list -deps` + call paths; требует per-symbol различения (tokenizer ≠ tree-parser), dep-internal callers, mode-gate по конструктору | машинный falsifier (контракт §8 покрыл один подкласс) |
| **Исключённый тип/диапазон** — значение ограничено до sink (`CFG-BOUND`, `CFG-EXPR`) | GO-2026-4526 (атакующий контролирует документ, не выражение), GHSA-rm6m (prefetch гарды) (2/14) | provenance аргумента + перечень guard write-sites; источники конфига должны быть перечислены | частично машинно; provenance не замкнут |
| **Эффективная конфигурация** — условие выключено в deployment (`ADMIN` домен) | GHSA-33mj (protocol: tlsv1.0/1.1 переопределяет default), часть GO-2026-4526/rm6m | аудит **всех** источников конфигурации; админ-документация не устанавливает эффективное значение | досье эксперту + config-audit; автоматический негатив небезопасен |
| **Внешнее эксплуатационное допущение** (`TRUST`) | GO-2026-6372 (доверенный брокер), GO-2026-5970 (host из конфига, не от атакующего) | threat-model решение, не проверяемое статически | досье; никогда не автоматический негатив |
| **Платформа/toolchain** (`PLAT`) | GO-2026-5024 (GOOS-gate), GO-2026-5942 (диапазон toolchain) | build context снапшота (GOOS/GOARCH, `go version -m`) | машинный falsifier — уже покрыто платформенными условиями |
| **Детерминистические** (`FIXED`, SBOM-noise) | ~5 строк вне пула пользы | версия вне диапазона | не added value поверх govulncheck |

Выводы для направления инвестиций:

- Доминирующий класс — отсутствие кода (9/14), и именно под него лёг
  контракт §8. Остальные его подклассы (server-half API, tokenizer≠parser,
  dep-internal callers) требуют per-symbol reachability — более дорогого
  доказательства, чем package-absence, и отдельной проверки границ.
- `CFG-*` и `TRUST` (4/14) — не расширяются автоматически: для них
  осмысленен не checker, а досье с перечисленными источниками и open
  obligations.
- Класс «отсутствие кода» агрегирует разное: отсутствие пакета, отсутствие
  вызова и выключенный режим. Доля 9/14 сама по себе не обосновывает новый
  checker — для каждого кандидата сначала нужен baseline: сообщает ли
  govulncheck именно `reachable`, и какой дополнительный факт требуется для
  отклонения. Если govulncheck уже сообщает отсутствие вызова, это не
  добавленная ценность. Следующий checker оправдан только при повторяющемся
  конкретном факте, который текущий маршрут дорого/ненадёжно проверяет
  (условие продолжения из решения 2026-10-01): **один SYM-ABSENT-кандидат
  с подтверждённым reachable baseline и точным недостающим доказательством**
  — до этого анализатор dep-internal callers преждевременен.

**Выбранный кандидат (карточка в приватном реестре, POOL-A-02):
`GO-2026-4762`** — grpc `:path` authz bypass. Baseline: govulncheck
source-mode на продуктовом снапшоте — `reachable` до `Server.Serve`.
Недостающее доказательство — не SYM-ABSENT, а GATE-FEATURE: «продукт
не принимает authz-решений по `:path`/`FullMethod` нигде» — дефектный
сайт слинкован и достижим, поэтому package-absence неприменим; факт
раскладывается на package-absence `grpc/authz` (проверено механически)
+ перечисление server interceptor chain (1 сайт, 4 interceptor'а) +
экспертный просмотр ограниченного списка. Простой verifier покрывает
часть факта; checker оправдан только при повторяемости — на одном кейсе
ручное перечисление дешевле. Кейс выбран именно для измерения: если
на следующем срезе GATE-FEATURE встретится повторно, появится основание
для enumeration-checker'а.

Наблюдения из первого прогона на реальных снапшотах (публичные якоря):

- `GO-2026-6443`: анализатор выдал `EXPLOITABLE` на продукте без xDS —
  в модели отсутствует mandatory-условие «режим включён», а нерезолв
  root-cause кандидата молча сузил множество условий. После фикса B30
  (коммит `analysis: unresolved in-scope advisory sinks block
  EXPLOITABLE`) тот же снапшот даёт `INCONCLUSIVE` с именованным
  `internal/xds/server.RouteAndProcess`; положительный вердикт на
  неполной модели закрыт, отрицательный — ещё не доказан.
- Тот же advisory на втором снапшоте: `INCONCLUSIVE` из-за
  неподдерживаемого формата fix-ссылки (`github.com/.../pull/NNNN`) и
  ошибок package loading на реальном dep-графе. Формат `pull/NNNN`
  поддержан; ошибки загрузки (CGo-биндинги без клиентских библиотек)
  корректно остаются `INCONCLUSIVE`, а не `UNKNOWN`-негативом.

Эти факты мотивируют исследование: сильные кандидаты класса
`GATE-FEATURE`/`SYM-ABSENT` существуют на reachable-сигнале, но текущий
пайплайн их не резолвит (и в одном случае неверно закрывает в
положительную сторону).

## 8. Контракт отрицательного доказательства: defect-locus отсутствует в build graph

Следующий срез проверяет одно основание отклонения и ничего больше:
дефект advisory не может проявиться, потому что код, в котором он живёт
(defect locus), не входит в build graph снапшота продукта. Контракт
разделяет два независимых обязательства; оба должны быть замкнуты,
иначе результат `INCONCLUSIVE` (или досье), а не негатив.

### 8.1. Обязательство necessity: локус необходим для этой CVE

Множество локусов `L` — функции/участки кода, исполнение хотя бы
одного из которых необходимо для проявления именно этого дефекта.
Требования к установлению:

- `L` выводится минимум из двух независимых якорей: advisory-declared
  affected symbols И дефектный участок в fix-diff ИЛИ regression-тест;
  «функция изменена в патче» само по себе не доказывает необходимость —
  патч может менять защиту, вспомогательный код или несколько механизмов.
- Enabler-функции (патч добавляет входную проверку на пути к дефекту)
  различаются с defect site: необходимость привязывается к месту, где
  живёт само уязвимое действие, а не к любому изменённому файлу.
- **Замыкание по declared-множеству:** машина никогда не исключает
  declared-символ из `L` автоматически. Текстовый body-scan не доказывает
  отсутствие сайта: отсутствие совпадения означает лишь «соответствие не
  установлено» — переименование переменной (`mdata`→`headers` в
  review-контрпримере) или алиас через целую структуру разрывают
  межфункциональное сопоставление операнда. Поэтому `L` = declared set
  **минус экспертные исключения**: `NonLocusBasis` — записанные решения
  «символ не является defect locus» с обоснованием и authority; они
  участвуют в разрешении falsifier'а как экспертный ввод и попадают в
  отчёт отдельным блоком (verification фиксирует их наличие в
  limitations, но не проверяет истинность основания).
- Fix-diff anchors (guarded-site / enabler-candidate / fix-changed /
  not-fix-changed) остаются машинными **аннотациями** для разбора
  экспертом — `SymbolFaultingUse` помечает кандидатов, но не сужает `L`.
  Экспертное решение для символа вне declared set игнорируется с записью
  в limitations.
- Обязательство задокументировано: почему ни один путь модуля не
  достигает дефектного состояния, минуя `L`. Остаточное допущение —
  полнота advisory declared set (сайт вне declared symbols контракту
  невидим) и корректность экспертных исключений, если они заданы.
  Если необходимость не замкнута — контракт не применяется.
- LLM/человек могут предлагать привязку `L`; детерминистический слой
  проверяет структуру доказательства и отсутствие в build graph.
  Предложенная привязка без обязательств — не доказательство.

### 8.2. Обязательство absence: код отсутствует в полном build graph

Отсутствие доказывается по графу сборки снапшота, а не по косвенным
признакам:

- Источник истины — полный build graph продукта (`go list -deps` или
  эквивалент) с фактическими GOOS/GOARCH/build tags/toolchain снапшота;
  отсутствие пакета локуса в графе — кандидат-фальсификатор.
- Ошибка загрузки пакета, неразрешённый symbol, неполный/несогласованный
  vendor-листинг, падение `go list` — это `UNKNOWN`, а не отсутствие.
  Для vendored сборок vendor-дерево — доказательство только после
  проверки согласованности с `go.mod` (`modules.txt` как минимум).
- Проверка на уровне пакета в графе, а не call-site pattern: обход через
  wrapper/callback/альтернативный entrypoint сохраняет пакет в графе и
  обязан ломать основание.
- Пакет локуса присутствует в графе, но сама функция недостижима —
  более сильное утверждение, этим контрактом не покрывается:
  результат `INCONCLUSIVE`, не NEPF.

### 8.3. Полнота и границы

- Фальсификатор обязан покрывать всё множество `L`, а не только его
  разрешённую часть; незакрытые члены `L` держат контракт открытым.
  `UnresolvedSubjects` нельзя снимать ради отрицательного результата.
- Контракт не расширяет ingress closure и не вводит правил, привязанных
  к конкретной CVE; класс — `GATE-FEATURE`/`SYM-ABSENT` по build graph.
- Отрицательный результат оформляется как обычный `VERIFIED` falsifier:
  названный falsifier, перечисленные обязательства, ограничения coverage
  и условия инвалидации сохраняются в отчёте.

### 8.4. Нейтральный пул и оценка

Проверяется на публичных зависимостях (`grpc-go`, `GO-2026-6443`) без
привязки к приватным проектам. Минимальный пул с сопоставимым
govulncheck `reachable` baseline во всех вариантах:

1. **mode-off** — продукт без `xds`: пакет локуса вне build graph →
   ожидается NEPF по контракту.
2. **mode-on** — `xds.NewGRPCServer`: govulncheck-трейс проходит через
   `RouteAndProcess` → основание не применяется, verdict не негативный.
3. **wrapper** — режим включён через wrapper/callback/косвенный
   entrypoint: call-site-проверка дала бы ложный негатив; build-graph
   проверка обязана сохранить сигнал.
4. **pkg-present** — пакет локуса в графе (импортирован), но функция
   недостижима: контракт обязан дать `INCONCLUSIVE`, не NEPF.

Успех среза — корректный NEPF на одном автоматизированном основании с
выдержанными контролями. Второй независимый advisory класса проверяет
переносимость. Оценка стоимости — сравнение с маршрутом
`govulncheck + LLM + исходники`: собственный механизм оправдан, только
если даёт доказательство, которого тот маршрут воспроизводимо не даёт.

#### Результат среза (GO-2026-6443, прогон после реализации)

Нейтральный пул `eval/corpus-real.json` — все четыре варианта прошли
по контракту:

| Вариант | analyzer | govulncheck | Контракт |
|---|---|---|---|
| real-micro-plain-6443 | **EXPLOITABLE** — сигнал сохранён, не подтверждение эксплуатации (без basis весь declared set в L; HandleStreams в трейсе → `C-LOCUS` TRUE) | reachable (`HandleStreams`) | автоматическое исключение запрещено — машина совпадает с govulncheck |
| real-micro-plain-6443x | **NO_EXPLOIT_PATH_FOUND** | reachable | expert `non_locus` на HandleStreams+operateHeaders записан в модель → `C-LOCUS` FALSE + `locus-package-absent` VERIFIED |
| real-micro-xds-6443 | EXPLOITABLE | reachable (`RouteAndProcess` в трейсе) | `C-LOCUS` TRUE — сигнал сохранён |
| real-micro-wrap-6443 | EXPLOITABLE | reachable | factory-обёртка не ослабила: module-internal chain доказал локус |
| real-micro-pkg-6443 | INCONCLUSIVE | reachable | пакет в графе, функция не вызвана → `C-LOCUS` UNKNOWN, NEPF не выносится |

На реальном вендореном снапшоте (grpc v1.80.0, `internal/xds` отсутствует
в vendor): `RouteAndProcess` не резолвится в source → `UnresolvedSubjects`,
но он ∈ L; без экспертного basis транспортные символы остаются в L и
достижимый declared символ даёт `C-LOCUS` TRUE → EXPLOITABLE (сигнал
сохранён — текущая модель не подтверждает эксплуатацию); с записанным
basis на transport-символы → NEPF через coverage-гейт
`locusCoversUnresolved` (прогон `case-snap-6443-v3`: NEPF, basis-блок
в отчёте, limitation о сокращении coverage записан). Verdict-кейс:
EXPLOITABLE (до B30) → INCONCLUSIVE (B30-блокер) → NEPF **при участии
записанного экспертного основания** — автоматический негатив без него
больше не выносится (review-контрпример зафиксирован ниже).

Переносимость: `GO-2026-6061` (xDS RBAC + transport, два дефекта в одном
advisory) — boundary-кейс: fix-changed transport-символы остаются в L,
их пакет слинкован в любой grpc-сборке → falsifier не покрывает →
контракт корректно не даёт негатив. Второго *положительного* переноса
нет: нужен advisory, чьи все дефектные сайты живут в опционально
линкуемых пакетах — редкая форма.

Стоимостная оценка: `govulncheck` не выносит mode-off отклонение (трейс
останавливается на первом declared-символе), `LLM + исходники` может
сформулировать ту же гипотезу, но без machine-verifiable доказательства —
контракт даёт persisted VERIFIED-запись с явными границами build context.
Один класс дефекта (guard перед faulting op) и одно основание
(package-absence) — вывод о регулярной пользе не делается.

#### Проверка границы necessity (2026-10-01, нейтральные контроли)

Первая попытка замыкания (body-scan declared-not-changed символов по
operand-семейству) была **опровергнута review-контрпримером**:
переименование локальной переменной в непропатченном сайте
(`mdata`→`headers`) разрывало текстовое сопоставление — сайт исключался
из `L`, falsifier выдавал ложный `VERIFIED` NEPF при живом дефекте.
Вывод: текстовое несовпадение — это «соответствие не установлено»,
не доказательство чистоты; межфункциональную необходимость машина
замыкает только экспертным основанием. Финальная семантика:
`L` = declared set − `NonLocusBasis` (записанные экспертные решения).

| Контроль | Механика | Результат |
|---|---|---|
| Неполная fix series (`legacyRoute` — declared, не в diff, тело индексирует операнд) | автоматического исключения нет — символ остаётся в `L` при любом написании | falsifier не покрывает слинкованный пакет → `INCONCLUSIVE` |
| Rename-контрпример (`a := headers[":authority"]; a[0]`) | текстовое несовпадение не снимает обязательство | сайт в `L` → `INCONCLUSIVE`; NEPF только через экспертное исключение |
| Два независимых дефекта (L = {xds-сайт, transport-сайт}; xds-пакет отсутствует, transport слинкован) | falsifier требует отсутствия **всех** пакетов L | `C-LOCUS` UNKNOWN → `INCONCLUSIVE` |
| Upstream-only fix (diff трогает только enabler) | сайт не в diff → остаётся в `L` | falsifier обязан покрыть transport+xds → `INCONCLUSIVE` |
| Экспертное основание (`non_locus` на transport-символы) | `L`={RouteAndProcess}, решения записаны в модель и отчёт | falsifier покрывает оставшийся пакет → `NEPF` с записанным basis |

#### Разделение эксперт/машина (ledger)

Машина проверяет (persisted, replayable):
- membership символа в advisory declared set и в fix-diff hunks;
- anchor-аннотации (guarded-site / enabler-candidate / fix-changed /
  not-fix-changed) — сигналы для эксперта, не исключения;
- присутствие/отсутствие каждого пакета `L` в persisted
  `go list -deps` графе снапшотного build context;
- покрытие `UnresolvedSubjects` множеством `L` для NEPF-гейта;
- что falsifier-овер coverage уменьшался только записанными решениями.

Эксперт устанавливает (вне машины, требует записи в отчёт):
- полноту advisory declared set (дефектный сайт вне declared symbols
  контракту невидим);
- non-locus решения по каждому исключаемому declared-символу —
  с текстом основания и authority (`non_locus_basis`);
- корректность самого fix (что патч действительно чинит объявленный
  дефект).

#### Сравнение маршрутов на одном кейсе (GO-2026-6443, вендореный снапшот)

Одинаковые исходные данные: advisory + fix-diff PR9365 + snapshot source +
`go list -deps` + govulncheck. Выбор кейса удобный (контракт под него и
писался) — вывод ограничивается осуществимостью, не регулярной пользой.

| Измерение | Analyzer (B30-контракт) | `govulncheck + эксперт + go list` |
|---|---|---|
| Решение | `NO_EXPLOIT_PATH_FOUND`, falsifier `locus-package-absent` VERIFIED | то же отклонение возможно: эксперт устанавливает локус по diff, проверяет `go list -deps \| grep` |
| Оставшиеся допущения | зафиксированы в отчёте: полнота declared set + каждое expert non-locus решение поимённо | те же допущения — но неявные и не записанные; повторный аудит требует повторного вывода |
| Ручная подготовка основания | necessity **не** замыкается машиной — экспертное `non_locus` обоснование обязательно; машина даёт anchor-аннотации и проверяет absence | эксперт читает advisory, diff и код сайта вручную; отсутствие подтверждает тем же `go list -deps` |
| Проверка отчёта третьей стороной | falsifier и expert-решения ссылаются на persisted evidence — проверяются без повторного вывода | повторный вывод с нуля или доверие тексту тикета |
| Стоимость механизма | канал решений, верификатор, контроли — реализовано и поддерживается | один узкий verifier («пакет X вне go list -deps?») поверх экспертно заданного L покрыл бы этот класс |

Вывод измерения (уточнён после review): автоматизация **части** работы
показана — машина собирает evidence, аннотирует anchors, проверяет
absence и хранит replayable запись с поимёнными экспертными решениями.
Величина экономии **не установлена**: necessity по-прежнему закрывает
эксперт (теперь — явно записанным основанием), а доказательственное ядро
«пакет локуса вне графа» покрыл бы и тривиальный verifier. Дифференциальная
ценность собственного механизма против `verifier + expert basis` — тема
следующего среза, не установленный факт.

**Текущая роль B30 (после P0-закрытия):** модуль проверяет машинную часть
экспертно подготовленного основания — привязку `L`, absence по графу,
replayable запись и границы ошибки. Самостоятельное получение
дополнительного отклонения поверх govulncheck **не показано**: без
экспертного basis вердикт совпадает с исходным сигналом (EXPLOITABLE —
«сигнал сохранён»). Расширение анализатора остановлено; следующий шаг —
выбор одного кандидата по карточке недостающего доказательства (§7.1):
snapshot + build context + Go, сырой `govulncheck: reachable`, достаточное
экспертное основание отклонения, конкретный факт вне текущего модуля,
возможность проверки простым verifier'ом.

### 8.5. Artifact fidelity

Выводы по реальным снапшотам остаются source-only до верификации
артефакта сборки. Рабочее правило: явно указанному в тикете runtime
доверяем; source-проверку запускаем соответствующей версией Go и
подтверждаем её в JSON `govulncheck`. Это не устраняет возможное
расхождение исходников и зависимостей с конкретной сборкой — такие
результаты помечаются provisional и не считаются доказательством
класса без замечания.
