# Генеральность: никакого case-specific хардкода

Читать перед добавлением эвристик/таблиц в `internal/` — особенно
`internal/goanalysis` (knowledge-base семантики экосистемы).

## Правила

- Никаких идентификаторов конкретного продукта/кейса в коде: имена
  пакетов, функций, полей и конфиг-ключей анализируемого репозитория не
  зашиваются в таблицы и условия. Если запись верна только для одного
  кейса — это не knowledge, это чит.
- `goanalysis.Knowledge` — только универсальная семантика экосистемных
  API (stdlib, широко используемые фреймворки/декодеры/драйверы):
  `os.Getenv` → CONFIGURATION, `io.ReadFull` → (dst,src), теги
  `mapstructure`/`env` → конфигурация. Аналог — CodeQL Models-as-Data.
- Расширение — сначала через `--knowledge <json>` (аддитивный мерж,
  конфликт ключа = ошибка). Новые дефолты в `DefaultKnowledge()` —
  только для широко стабильных API, не для API встреченного в одном
  живом кейсе.
- Направление ошибки консервативно: пропущенная запись → UNKNOWN
  (безопасно, limitation), неверная запись → неверный origin (опасно).
  Поэтому внешняя база не может переопределить встроенные записи и
  валидируется при загрузке.
- Паттерны exploit-моделей (`internal/exploit`) живут по тому же
  принципу: registry entries — классовая семантика, не кейс.
