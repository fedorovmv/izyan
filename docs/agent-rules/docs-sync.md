# Документация — синхронизация с функционалом

Читать перед работой в `docs/` и при закрытии бэклог-пунктов.

## Структура `docs/`

- `dev/specs/` — нормативные спецификации и контракты системы (меняются осознанно и редко)
- `dev/decisions/` — принятые архитектурные решения (ADR)
- `dev/plans/` — активные стратегические планы и роадмапы будущих фич (`*-plan.md`)
- `dev/current/` — живое состояние разработки: `implementation-status`,
  `gap-analysis` (бэклог), `analysis-internals` (механика)
- `dev/history/` — исторический архив: начальный bootstrap, архив завершённых планов (`history/plans/`) и архив дизайн-спецификаций реализованных фич (`history/specs/`)
- корень `docs/` — документация для пользователей (`INDEX.md` — навигатор)
- [`eval/README.md`](../../eval/README.md) — корпуса и бенчмарки (вне `docs/` — рядом с данными)
- `agent-rules/` — эти правила (на уровне `docs/`, не в `dev/` —
  читаются при любой задаче, не только девелоперской)

## Правила

- Каталог `docs/superpowers/` запрещён: новые спецификации пишутся в `docs/dev/specs/`, а планы — в `docs/dev/plans/`.
- Жизненный цикл планов и спецификаций:
  - **Дизайн-спецификации фич**: после реализации и приёмки функционала переносятся в архив `docs/dev/history/specs/<name>-design.md`. В `dev/specs/` остаются только действующие нормативные контракты системы.
  - **Стратегические планы (роадмапы)**: после закрытия всех пунктов переносятся в `docs/dev/history/plans/<name>-plan.md`.
  - **Пошаговые планы реализации (TDD-чек-листы с микро-тасками)**: являются временными рабочими артефактами; после успешной реализации и прохождения тестов **удаляются**, а не остаются в репозитории.
- [`dev/current/gap-analysis.md`](../dev/current/gap-analysis.md) — канонический бэклог: §1 пробелы
  спека↔код, §2 открытые пункты с done-критериями + handoff
  notes. Закрытие пункта = удаление строки из §2 в коммите закрытия;
  историю в файле не храним (она в `git log` и планах); новая находка —
  в §2 с приоритетом.
- Новая фича с нетривиальным дизайном → план в [`dev/plans/<feature>-plan.md`](../dev/plans/<feature>-plan.md)
  (имя по сути фичи) + строка в [`INDEX.md`](../INDEX.md) + ссылка из
  бэклог-пункта в §2. Не плоди документы для мелких правок — мелкое
  идёт прямо в `gap-analysis`/[`eval/README.md`](../../eval/README.md).
- [`eval/README.md`](../../eval/README.md) — обновляй при изменении поведения
  на живых кейсах (что доказано, что UNKNOWN и почему).
- Фиксируй: какие claims детерминистические, что доказывает negative
  verification, где скан неполон, как dynamic маркеры влияют на
  уверенность.
- Пути и имена приватных репозиториев не коммитятся: продукт-кейс —
  `${VA_PRODUCT_REPO}` / «продукт-референс».
