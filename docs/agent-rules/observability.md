# Метрики, трасировка, аудит

- Тайминги каждого state пишутся в кейс (`timings:` строка в выводе и
  отчёт) — новые стадии/тяжёлые операции замеряй.
- `llm_calls` инкрементируется на каждый вызов; бюджет `MaxLLMCalls`
  уважается — при исчерпании честный limitation.
- `tool_executions` + `ToolVersion` аудит — exec-инструменты и
  версии toolchain пишутся в EvidenceGraph; reproducibility: тот же
  вход → тот же детерминистический выход.
- Limitations — первоклассные граждане: каждое упрощение анализа
  записывается в claim/case limitations и видно в отчёте, а не
  теряется в логах.
- Отчёт показывает историю доказательств: demoted-claims отображают
  `falsifier / VERIFIED (demoted)`, не только финальный результат.
- Прогресс длинных операций — на stderr, отчёты — в файлы; stdout
  чистый для пайплайна.
- Отчёт самодостаточен: каждый вердикт/claim называет проверенный
  предмет (модули — `CheckedModules`, пакеты — `CheckedPackages`,
  условия — ID в reason), семантику проверки и охват
  (напр. «absent from `go list -deps -test ./...` transitive closure»),
  и ссылается на evidence-id. Голый код результата без предмета и
  метода — дефект отчёта.
- Поля `AffectedResult` интерпретируются по зафиксированной семантике,
  не по названию: `package_present=FALSE` = «все `CheckedPackages`
  отсутствуют в транзитивном замыкании сборки, включая
  build-constraint-excluded файлы» — код не линкуется в продукт.
  Отвечая на вопрос по кейсу, опирайся на артефакты (`report.json`,
  evidence, `Checked*`-поля), а не подменяй их собственным прочтением
  кода — ручной разбор не заменяет проверенный факт и не должен
  ему противоречить без ослабляющего артефакта.
